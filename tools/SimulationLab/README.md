# AGV 仿真测试中心

仿真测试中心让正式 Service、任务接口、Outbox、SQLite、Robokit TCP 和 S7 采集写入连接本机虚拟设备。虚拟车辆收到运输命令后沿路线运动，虚拟 PLC 根据设备到位、箱体和倒料计时产生反馈。控制器不通过改任务终态、改数据库或移动坐标使业务“通过”。

日常操作入口保持 **http://127.0.0.1:5199/#/simulation-center**，从“工程工具 → 仿真测试中心”进入。私有调度实例使用临时端口、独立管道与数据库；这些端口用于隔离验证，不是另一个日常版本。初次准备工具还会生成临时控制台，用于安装前验证；同一个仿真实例只能由一个控制台管理。

## 日常最快路径

1. 打开“环境与地图”，点击“拉取当前运行地图”。页面复制当前有效地图、道路曲线、资源配置、工位/等待位/倒料位和当前车辆参数；随后选择与这张地图对应的 PLC 点表 CSV，或显式载入当前隔离实例自己的点表副本。页面会展示工位、点表数量、来源和 SHA256；不再默认读取仓库全局点表，也不会套用现场后台的实验室文件。
2. 核对检修点、资源边界和每辆车唯一初始Station，点击“创建自定义隔离实例”，再点击“启动仿真环境”。
3. 进入“场景编排”，选择“正式调度持续排队测试”。验证双车忙车排除建议使用 **2辆虚拟车 + 3个工位 + 至少6次连续呼叫**，其中第3工位必须明确显示“隔离合成点位”。全部工位已在当前有效点表确认时，可配置更多工位和多轮呼叫。
4. 运行结束后查看“恢复与报告”。失败时报告给出第一失败原因、卡住步骤、车辆等待链和恢复后应观察的反馈；历史页可载入同一轮采样地图进行时间轴回放。
5. 常用地图、车辆、工位、优先级、PLC 点表和场景可在“保存方案，下次直接开测”中命名保存。方案同时记录地图 ID/版本/摘要、任务拓扑、完整点表内容和点表哈希；先选方案，再点“一键开测”，系统会创建干净实例、生成实例专属 `simulation-signals.csv`、启动环境并提交该方案场景。删除方案只删除配置，不删除历史实例和报告。

## 日常使用

1. 打开仿真测试中心，先核对顶部的“当前仿真方式”、实例名和“NEXT 下一步”。页面按“运行总览 → 环境与地图 → 场景编排 → 故障注入 → 恢复与报告”分阶段，不再把全部配置同时铺开。
2. 需要更换拓扑时进入“环境与地图”。可一键拉取当前运行地图，也可导入当前格式 `.agvmap.json`；页面支持1–32个业务工位、每工位派车优先级、唯一取货点、主/副等待位、倒料点、倒料资源边界和检修点。车辆行可配置编号、唯一初始Station、包络半径、初始电量、初始载箱、速度倍率及2–20点电池电压曲线，数量为1–8。点击“创建自定义隔离实例”，核对新实例名后再启动仿真环境。
   也可导入 ProfControl 只读 `.rpj`：转换站点、直线/贝塞尔/多边形圆弧路径、控制区和车辆元数据；圆、矩形、图片、信号发生器等视觉对象会列入未转换清单，不会伪装成等价功能。
3. 在总览启动环境，然后进入“场景编排”选择场景、轮数、间隔和超时。第一次建议用完整业务循环、1轮、600秒超时。右侧会说明本场景要验证什么、需要观察哪些证据；运行后总览显示地图、当前轮数、任务阶段与等待信息。
   “正式调度持续排队测试”只产生工位PLC呼叫，不指定车辆，也不直接创建任务或写入调度数据库。正式 CreationCoordinator 接单，正式调度按在线、空载、无原任务、无残留路权、可达路线和工位优先级选择车辆。同一工位已有原任务时，后续呼叫保留在场景计划队列；其他工位继续追加。忙车期间仍存在正式待派任务，才算真正覆盖积压。
4. 查看“自动检查与报告”。报告有场景名、原报告编号及完成时间。新场景运行期间，上一场景的报告会明确标为历史结果，不能拿它判断本次已通过。点击“导出报告 JSON”保存结果。
5. 同一环境内，任务和 PLC 正常闭合后可以继续运行其他场景。需要人工故障测试时进入“故障注入”，使用车辆、PLC 和道路控制；观察实际反馈编号，而不是仅看请求提交成功。
6. “通用协议虚拟服务器”接受声明式 JSON，支持 TCP/UDP/HTTP、行或4字节长度分帧、JSON子集/文本/正则匹配、状态变量、模板响应、延迟、丢响应和断连。脚本只能绑定回环地址且不执行任意代码。页面可复制监听端口给外部协议客户端。
7. “电梯/门/信号发生器”是可选独立设备模型，支持两层运行、开关门、故障/复位、即时信号和多时点信号时间轴。它当前不改变正式派车、PLC 契约或安全联锁。
8. 完成后点击“停止仿真环境”。原数据库、任务、设备快照、路权和日志保留。在“环境与地图”可沿用当前地图快速新建，或导入新地图和车辆配置。此操作创建新的相邻目录，不清空或覆盖旧现场。

“中止后续场景”停止继续提交呼叫和后续编排，已下发任务及其占用保留。它不是车辆急停，也不会把原任务改成完成。网络断开同样不等于物理停止，设备模型可能继续执行已经接收的运输。

设备数据过期或控制器断开时，页面保留历史观察并禁用新场景及设备故障写入。先刷新原记录、查实例日志，再判断后续操作；不要把旧位置当作车辆当前已停稳。

## 自动场景

| 页面场景 | 实际执行 | 预期结果 |
| --- | --- | --- |
| 完整业务循环 | 两个已建模工位依次呼叫、创建原任务，完成取满箱、等待、倒料、返空箱和握手闭合 | 原任务九步完成、每任务四次运输、PLC闭合、租约释放 |
| 多工位同时呼叫 | 两个工位P侧呼叫由同一批输入在同一次虚拟设备扫描中置位，等待设备确认原批次后通过正式接口建单 | 两个原任务正常完成，采样中没有资源超容量或合成车体包络重叠；批次输入和设备确认保留为证据 |
| 自定义呼叫计划 | 按用户设置分时间、分工位批次产生P侧呼叫，自动选择可达车辆或核对指定车辆，再通过正式接口创建任务 | 计划内全部原任务完成，原命令、设备3066接收、PLC和路权闭合 |
| 正式调度持续排队测试 | 场景只持续产生PLC工位呼叫；正式后台自主建单和派车，同一工位不提前重复置位 | 记录忙车期间待派队列、派车顺序、同一车不承担两个未结束任务、持续消化和最终闭环 |
| 车辆断连与重连 | 原任务持有路权且相关运输正在执行时断开车端通信，约5秒后恢复，并核对设备控制反馈 | 原路权保留、恢复原运输身份、业务最终闭合 |
| PLC反馈延迟 | 建单前等待设备确认 Ready 3秒、Done 8秒的控制，再运行业务 | 延迟确实生效且原任务闭合；成功后恢复默认5秒Done |
| PLC卡位与恢复 | 原任务到达等待Ready或完成Done后阻止对应信号1–120秒，随后解除并继续观察 | 卡位实际生效、原任务未跳步、恢复后原任务闭合 |
| 后台重启与恢复屏障 | 活动运输持有路权时重启本实例 Service | 原任务、原命令和路权保留，恢复屏障未自动放行。**结束时保留活动任务待核对，不是完整业务循环完成。** |
| 恢复后继续原任务 | 恢复面板逐项核对并放行后，不新建任务，只观察原任务编号续接 | 原九步完成、原命令未替换、最终PLC与路权闭合 |

普通场景支持1–100轮、轮间隔0–60秒、单次等待超时30–3600秒。重启和恢复续接场景只能运行1轮。自定义呼叫和持续排队提供按时间、工位和最多500次呼叫编排；任意步骤条件编排仍需后续通用时间轴。

后台重启后，“现场式恢复核对”展示私有后台实际恢复条目。逐条选择继续原节点、补记物理完成或关闭取消，填写物料引用与原因并勾选车辆位置、载荷归属和PLC周期。只有所有条目已核对才可放行。这些勾选记录的是隔离模型上的人工决策，不替代现场身份、箱体容器和机械核对。

持续排队场景和正式PLC自动接单都不直接插库。场景前核对完整任务汇总、空载静止及PLC闭合；遇到未闭合状态不自动批准活动任务恢复。保留异常证据后，使用新干净实例重测。

## 人工故障怎么用

先选择目标虚拟车。暂停/恢复运动只控制运动模型；断开/恢复通信只控制网络。倍率范围0.1–10。丢弃下一响应只作用于下一次成功接收的3066运输命令：命令已经进入模型队列，但连接关闭、不返回响应。它是一次性故障，不作用于普通查询；消费后不应因其他控制请求再次触发。

展开“道路阻塞”，勾选当前地图中的道路ID，点击“应用道路阻塞”。模型会在该车经过对应道路时停止运动；“解除所选车全部道路阻塞”只撤销所选车的道路列表，不清其他车的故障。地图中的已反馈阻塞道路显示为橙色虚线。

PLC控制提供Ready/Done延迟（0–300秒）、阻止/恢复Ready、阻止/恢复Done、设备故障注入/撤销。控制请求使用唯一序号，页面显示设备实际应用的序号与拒绝原因。PLC的调度输出仍由正式后台负责，不提供修改H输出、跳步完成或重置任务的按钮。

人工故障撤销后，只要设备和任务实际闭合，就可继续自动场景；PLC反馈延迟恢复Ready 0秒、Done 5秒，故障及阻止反馈恢复为关闭时，按默认设置核对，不因控制记录存在而拒绝。故障阻塞导致场景超时或中止且仍有未闭合任务时，先导出证据，再停止环境并建立新干净实例，避免带着未知PLC、任务或资源开始下一次测试。

本地ProfControl授权测试材料中的 `VirtualHelper`、`AgvVirtual`、`MotorVirtual`、`BatteryVirtual`、`SignalGeneratorVirtual` 和 `ElevatorVirtual` 已用于能力对标。当前已在独立仿真边界内实现通信回环、车辆状态、速度倍率、加减速、电量、2–20点电压曲线、充电增益、电梯/门、信号发生器和仿真倍率。ProfControl类型依附其专有WPF地图、通信脚本和全局模型，本项目只独立实现对应行为，不复制反编译源代码或授权实现。

## 一次性准备（开发维护人员）

从 `DispatchingSystem` 目录执行。需要Windows、.NET 10 SDK、Python 3、本机有效HSL授权，以及本机已经维护的夹具地图/点表。准备脚本使用当前 `WebSingleVehicleLab`/`WebTwoVehicleLab` 模板；来源文件不可用时明确失败，不从旧资料补造。授权码由本机已有配置提供，不写进Git或携带包。

```powershell
# 前端依赖已经安装时直接构建
npm --prefix AgvDispatch.Web run build

# 初始基准包准备；日常自定义1–8辆和地图优先使用页面
python tools/SimulationLab/prepare.py --name web-single-vehicle-sim-你的新实验名 --vehicles 2
```

脚本依次发布Service/WebHost，再写回私有运行配置，生成 `artifacts/<新实验名>/simulation-package.json` 和临时 `启动仿真控制台.cmd`。准备不会连接或复制日常数据库，也不会改根启动指针。`--no-publish`只用于配置检查，产物不代表可运行发布包。

隔离验证时，可以用生成的临时控制台；其URL记录在 `simulation-package.json`。正式接入5199后，使用5199中的仿真页，不再启动同一实例的临时控制台。不要同时手工运行 `start_runtime.py`、设备模型、控制器和页面管理同一实例；端口冲突时检查归属，不能批量结束同名Service/WebHost。

控制器在 `Web:Simulation` 下配置 `Enabled`、`Root`、`PythonPath`、`ControllerPath`、`Port`。Root必须是本工程 `artifacts/web-single-vehicle-*` 的直接子目录；Python与控制器使用绝对路径。所有设备只允许 `127.0.0.1`，数据库、工程数据和管道必须属于该私有实例，端口不能使用5198或5199。WebHost内部创建私有令牌管理控制器，不需要在浏览器填令牌。

## 受控接入日常5199

使用 `tools/Apply-SimulationWebPatch.ps1`，不要手工覆盖活动发布目录，也不要另起5198作为新版。该脚本分“暂存检查”和“应用”两步；暂存会核对日常进程/版本、空闲任务及恢复状态，在线备份SQLite、通信配置、Web工程方案和原程序/启动记录，并生成哈希清单。

WebHost补丁须针对当前日常发布的共享程序集引用构建，`InformationalVersion`保持日常清单中的releaseId，依赖DLL与基线逐字节一致。此批为 `commissioning-20261104-014340`；不能把另一版Application/Domain DLL混入Web补丁。前端应使用已验证的构建目录。

以下是参数模板，绝对路径和空闲控制端口由维护人员填入；`PatchDirectory`必须是全新的目录，且不能与发布、运行数据、载荷或实例目录互相包含。

```powershell
# 仅暂存、校验与备份，不切换当前Web
./tools/Apply-SimulationWebPatch.ps1 `
  -BundleDirectory '<当前完整日常发布目录>' `
  -PatchDirectory '<新的补丁暂存目录>' `
  -WebPayloadDirectory '<使用原程序集引用编译的WebHost载荷目录>' `
  -StaticPayloadDirectory '<已验证的AgvDispatch.Web/dist绝对目录>' `
  -SimulationRoot '<新仿真实例绝对目录>' `
  -PythonPath '<python.exe绝对路径>' `
  -SimulationPort <未占用的临时端口>

# 对同一个已审查暂存目录应用
./tools/Apply-SimulationWebPatch.ps1 `
  -BundleDirectory '<同一个日常发布目录>' `
  -PatchDirectory '<同一个补丁暂存目录>' -Apply
```

应用只切换归属核对过的日常Web进程，保留原Service运行；前后核对5199版本、地图、工程存储身份和后台PID。根 `启动最新版Web.cmd`、`停止最新版Web.cmd`、`最新版Web.json` 仍是唯一日常入口。应用失败时查看脚本结果和原备份，不把暂存完成描述为日常已更新。

## 报告与问题复现

当前实例的 `simulation-report.json` 保存最近一次结果；每场景的 `simulation-run-<编号>` 目录保存原场景参数、创建请求/响应、原任务身份、只读命令记录、任务完成快照、独立观察、故障/恢复证据、报告和文件哈希清单。具体文件以实际场景产生的清单为准，未运行的分支不补造证据。

方案级 PLC 绑定还会在实例根目录保存 `plc-signals.source.csv`，并在 `service/config/simulation-signals.csv` 生成只含本次工位和倒料点的隔离副本。每轮证据目录保存 `plc-signal-table.json`、`plc-signals.source.csv` 和 `simulation-configuration.json`；报告记录地图 ID/版本/摘要、点表文件名、来源副本 SHA256、隔离点表 SHA256、工位数量及信号数量。仿真运行不会回写来源点表。

虚拟设备原始命令和事件在实例及 `robots/<车辆ID>` 的 `device-events.jsonl`；子进程输出在 `simulation-*-stdout.log` / `simulation-*-stderr.log`。高频查询日志有轮转，不能称为完整抓包。导出JSON只是结果摘要，排查时应连同对应场景目录、实例配置和原始日志保留。哈希清单证明包内一致性，不证明真实设备行为。

报告 `passed`表示该报告列出的模型检查满足；`failed`保留失败证据；`aborted`是中止，不是通过。重启场景还须看 `recoveryHold` 与 `completedBusinessCycle`：前者成立、后者不成立时，含义是恢复屏障正确保留，不能声称任务已经正常完成。

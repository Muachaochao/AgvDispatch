# PLC握手信号责任与时序草案

日期：2026-10-18。状态：供软件与PLC工程师共同核定；不代表现场协议已批准。

本次只整理契约，不修改地址、PLC程序、信号CSV、任务执行器或写入开关。13项是一个排屑工位的8项与一个倒料设备的5项逻辑信号，不是全现场只有13个地址。不同设备的Faulted是不同信号。

依据：当前`AgvDispatch.Service/config/plc-signals.csv`、`PersistentHandshakeExecutor.cs`、`PersistedHandshakeConditions.cs`、`TaskHandshakeContracts.cs`。持久化新握手是独立开关及版本契约，不等于现场已启用；旧执行路径不能被描述为已经具备新契约的全部保证。

## 1. 先统一原则

1. 每个字段只有一个业务写入方。该方负责置位、保持和复位；另一方通过自己的字段确认。复位条件由对方触发，不等于由对方直接清这个位。
2. 区分命令接收、设备执行完成、物理位置核实。写调用成功和输出回读均不是PLC业务确认。
3. 瞬时事件采用保持型请求/确认；物理状态由PLC持续计算，不强迫所有信号在任务末尾归零。
4. 双向区域按驱动实际写入粒度隔离。建议分别占用独立字节/字或DB区；实际分配需核实位写入与整字节读改写行为，不臆造新现场地址。
5. 同设备同一时刻只允许一个有效业务周期；任务、工位、设备、地图版本与周期绑定。PLC侧周期字段尚未提供，软件本地CycleId不能证明PLC确认属于同轮。

## 3. 两位握手的明确含义

示例使用逻辑名称，不分配地址：上位机写RemovedReq，PLC写RemovedAck。

|阶段|Req|Ack|规则|
|---|---|---|---|
|可开始|0|0|核实双方属于同一设备及周期基线|
|发起|1|0|上位机保持请求；PLC校验并记录一次接收|
|接收确认|1|1|PLC确认接收，不自动代表机械动作完成|
|请求撤销|0|1|上位机核实匹配确认后清自己的请求|
|闭合|0|0|PLC看到请求撤销后清自己的确认，允许下轮|

PLC发起满箱呼叫时，双方角色反过来。该例不等于13项各自都要新增一个Ack；状态类不配事件Ack，责任保持类按业务生命周期撤销。取箱/放箱通知目前最需要补显式确认。

掉电后出现任一组合，都不能仅靠这两个位判断本轮业务，必须结合周期、重启标识及持久化阶段。1/1不自动证明动作完成，0/1可能是待闭合，也可能是历史残留。

## 4. 建议的九步流程衔接

1. 满箱呼叫：PLC锁存请求；上位机持久化受理、去重并响应；完成本轮呼叫闭合，防止持续高电平重复派车。
2. 第一段运输至取货点：按业务节点→厂家Robokit站点映射到达，不能用PLC呼叫或发送成功代替AGV终态。
3. 取满箱：动作终态与BoxPresent=0共同核实；发送取箱通知；PLC业务确认仍需补契约；保持空箱返回责任。
4. 第二段运输至倒料等待点：车辆到站后发出等待请求，核对本轮设备归属。
5. 获得许可：区分设备能力状态和本车入站许可。优先建议独立能力状态与本轮许可；是否扩展字段由PLC方核定。
6. 第三段运输至倒料点：地图路权与设备许可共同门禁；许可的有效期、消费及撤回规则需明确。到位后启动本轮倒料握手。
7. 倒料：完成条件是PLC本轮Done，不是请求回读或接收Ack。完成后仍需按退出条件保留必要占用。
8. 第四段运输返回取货点并放空箱：核实AGV任务结果、实际站点、放箱动作与BoxPresent=1，通知PLC并核实接收。
9. 完成握手：按契约确认退出、清发送方通知、等待PLC结果撤销及基线闭合，才结束本轮。新呼叫单独受理，不吞掉新事件。

以上是业务衔接说明，不改变现有九步枚举或自动新增动作。尤其第5、6、9项必须与PLC时序共同核定。

## 5. 超时、故障及重启规则

|场景|拟议处理|当前实现边界|
|---|---|---|
|确认延迟/未到|保持本轮意图，显示等哪个信号、已经多久，不重新派发|超时阈值分“接收确认、设备动作、物理到位、闭合”，暂不填现场秒数|
|重复请求|相同周期及内容返回已有状态；同编号不同内容拒绝|PLC尚无已确认的周期接口，不能声称跨设备重启幂等已具备|
|历史Ack/Done为1|进入旧反馈核对，禁止将历史高电平当新完成|当前新执行器有部分低基线/新反馈检查；不能替代PLC周期身份|
|断连、采样过期或质量差|状态显示未知，阻止依赖该信号的新控制推进，保留责任和必要占用|缓存最后值不能充当当前有效反馈；已接受的设备动作需单独核实|
|写入调用后响应丢失|持久化写入待核对，读回只能证明当前值，再核实PLC消费与周期|新执行器写前记录WritePending，未知时禁止自动重发；不等于PLC已接收|
|上位机重启|读持久化任务、阶段、写入意图，再读取PLC与AGV状态核对，不启动时统一清零|新执行路径已有检查点；无PLC身份时部分场景必须人工核对|
|PLC重启/周期复位|检查PLC会话/启动标识与保持区策略；不能把复位后的0当作业务闭合证据|启动标识、保持属性与重启行为未获现场定义|
|任务取消|等AGV取消结果与现场核验，明确箱体/设备状态后逐项退出|取消请求不等于动作停止，也不直接清空箱责任或释放全部资源|

## 6. 后续字段及待核定清单

建议预留两块逻辑区域：HostToPLC与PLCToHost。按设备规划请求编号、命令类型、接收编号、执行状态、完成编号/结果、重启会话标识。心跳与通信质量另列，不承担业务Ack。字段类型、长度、字节序、多字段一致性/提交次序及掉电保持策略必须写入最终契约。

采用周期号时，PLC应在接收请求时锁存同批参数再确认；上位机必须核对确认编号和请求内容。不能只新增一个计数器便宣称解决重复执行。完成结果需要保持至发送方确认消费；同设备串行规则与取消后的新周期准入也需明确。

待PLC方核定：

- 13项唯一写入方，以及满箱请求重装条件；是否存在外部HMI/旧PLC逻辑同时写位。
- FullBoxRemoved与EmptyBoxPlaced的业务Ack采用独立位还是统一带编号的结果区。
- DumperReady是能力状态还是本轮许可；许可是否绑定车辆，何时失效及撤回。
- AgvAtDumpingPosition的真实语义，退出证据及允许撤销时点；如需实时位置与占用同时存在则拆字段。
- PLC启动标识、周期编号、掉电保持、通知/结果锁存、重复请求处理。
- 实际地址、驱动写粒度、采样频率、去抖、各阶段超时、字段更新一致性。

# 自研 AGV 调度实施顺序与现状分析

日期：2026-10-16
对象：快捷 AGV、Robokit TCP、现场 PLC、现有 AgvDispatch 主工程
性质：开发及联调计划。本报告没有修改程序、开启设备通信或执行现场控制。

## 1. 结论

继续使用现有 C#/.NET 10 后台和 WPF 客户端，自研项目所需的任务编排、PLC 联动和多车协调。不使用 RDS，按直接 Robokit TCP 的既定路线推进；现场是否另有厂家 Core 及其控制权占用，仍须在设备清单中查清，不能仅由“不使用 RDS”推断现场没有其他控制程序。

地图由厂家工具完成制作和单车调试，我方复用其有效地图、站点和路径，增加业务工位映射及交通资源配置。已有地图编辑和三维查看功能保留，首期不再以完整地图编辑、地图上传或三维能力扩展作为调度交付前置条件。

主要问题是开发重心和验证顺序需要收敛，不是技术栈需要重选。下一轮重点是把现有实现与真实地图、车辆动作、PLC 点位逐项对上，再证明完整业务能在真实设备上运行。

实施顺序：接口与职责核定 → 真实地图及业务映射 → 双侧只读采集 → 单车导航与动作 → PLC 联动完整任务 → 异常恢复 → 多车资源协调 → 有限范围试运行。

## 4. 软件和设备各管什么

| 对象 | 负责 | 交付边界 |
|---|---|---|
| 厂家实施工具 | 建图、站点/路径编辑、参数和车端任务/脚本配置、单车调试 | 提供实际有效地图及配置记录 |
| 车端控制器 | 定位、导航、底盘和车端机构执行、状态反馈 | 单车行为及接口语义由厂家确认 |
| 现场 PLC | 设备动作、传感器和设备联锁、约定的交接握手 | 上位机请求不替代设备内部联锁 |
| 我方调度后台 | 任务生成、派车、业务步骤、共享资源、两侧反馈核对、异常与记录 | 任务执行的唯一业务协调者 |
| WPF 操作端 | 查看、提交操作、显示等待原因和处置入口 | 关闭界面不应终止后台调度；界面动画不作为完成证据 |

正常调度期间的导航控制权归属需要明确，不能让 RoboShop、其他调度程序和我方后台同时竞争下发。调试切换应有可操作的交接步骤。

PLC 可能是一台总控管理多个工位，也可能有多个连接；不能按工位数量推断 PLC 台数。先核实际拓扑，不直接套用前面用于讲解的示例 IP。

## 5. 分阶段执行计划

### P0：先定接口和首期范围

目的：明确实际设备、控制责任和交付范围，避免按猜测修改程序。

工作：

1. 选定首期试点：一辆车、一个取料工位、一个倒料设备及必要等待位。多车场地和资源边界可同步调查，实际放行放在后续阶段。
2. 列设备清单：设备编号、控制器/PLC 型号、IP、端口、固件、网络接入方式、维护责任人。确认 RoboShop 安装版及是否存在厂家 Core 或其他控制端。
3. 确认谁控制取箱、放箱、倒料，各动作的启动方、完成证据、失败和复位条件。不能把现有测试中的 JackLoad/JackUnload 直接认定为实车动作。
4. 复核试点 PLC 点位的地址、类型、读写方向、置位/复位方、有效电平、保持/脉冲方式、超时及断电保持行为。
5. 收集本车原始地图文件、车端地图名/MD5/站点、真实接口返回和厂商行为说明。保留来源、时间、固件及文件哈希。

交付：设备通信表、动作责任表、试点 PLC 点表、首期验收清单。

出口：试点必需字段无未解释的推断项；资料缺失明确记“待核定”。未确认部分不映射为生产控制。

特别检查：现有 plc-signals.csv 的 sourceNote 包含从截图按数组步长扩展地址的说明。即使行内标为 Confirmed，也要核对现场程序或电气方确认记录，尤其是数组跨度和 DB 布局。只核首期实际使用范围，不要求先把全部工位资料补齐。

### P1：复用真实地图，建立业务映射

前置：P0 提供试点地图、站点和动作定义。

工作：

1. 厂家先在对应工具中确认实际车载地图和单车可行路线，交付原始文件。
2. 我方导入原图，保留源文件；如格式不支持，仅补当前图实际需要的解析能力，不重新造图。
3. 建业务工位—厂家站点对应表；业务编号、厂家站点号分别保存。
4. 核对米制单位、坐标原点、方向、角度、车辆位置参考点和本地显示变换。地图身份/版本和车端 MD5绑定按既有规则核定。
5. 核定实际使用道路的方向、直接连接及末站动作。我方生成的逐段指令必须符合车端地图，不能把前端画出的直线当作可执行路径。
6. 另建必要的共享区域/设备资源配置。厂家导航地图并不自动提供我方的工位容量、排队和路权规则。

交付：试点可用地图版本、工位站点映射表、路径/动作表、坐标核对记录、最少资源清单。

出口：所有试点站点及四段运输路线均明确；车端地图与后台绑定一致；缺失几何、方向或动作含义未通过核定时不启用该路段。

### P2：分别接通 PLC 和 AGV，只读核对

前置：P0 有有效通信参数；地图查询可与 P1 并行。

工作：

- PLC：验证连接、批量读、实际信号变化、断连/过期质量和恢复。软件显示的值必须与 PLC 在线监视一致。
- AGV：验证版本、控制权、位置、电量、报警、任务、地图/站点及载入状态；保留真实原始返回。
- 网络：验证有线与无线链路，按实际请求频率检查超时和恢复。不把 ping 成功当作协议接入成功。
- 对照端口：现有 S7 默认 102，Robokit 状态默认 19204、导航默认 19206；最终按实际配置使用。

交付：两侧只读采集记录、字段映射、异常质量展示及真实样例。

出口：正常值、断连和恢复都可解释；旧值不会继续被业务当成当前有效状态；此阶段不下发导航、不写 PLC。

### P3：一辆车，验证导航和实际动作

前置：P1、P2 通过，并完成现场调试条件及控制权交接。

工作：

1. 从简单的站点到站点开始，核对原任务编号、真实下发报文、车端接收/执行/完成状态。
2. 验证取货、等待、倒料和返程涉及的真实末站动作，以及车体方向和交接位置。
3. 核对暂停、继续、定向取消和失败反馈；回应成功不直接作为已停稳或已取消的证据。
4. 对当前路径核验保守拒绝的情况保留真实证据，例如 1303 规划结果不能直接证明指定两点相邻。修复应针对证据，不通过删除中间点或绕过门禁放行。

交付：试点路径和动作的实车记录、厂家协议差异清单及必要修复。

出口：车辆能够正确执行试点运输和必要机构动作，结果可通过车端及物理观察对应。导航完成与取放作业完成分开判断。

### P4：接通 PLC，跑完一条完整业务

前置：P0 的握手责任明确，P3 的导航与动作验证通过。

先手动创建一个任务验证全流程；再验证 PLC 呼叫自动创建，便于分离任务来源和执行故障。

| 业务环节 | 调度处理 | 完成证据 |
|---|---|---|
| 满箱呼叫 | 条件检查，落库建任务，再按约定应答 | 正确工位/周期仅生成应有的一份任务 |
| 派车取货 | 按地图与资源检查发送运输/取货动作 | 原车端任务完成及约定取箱证据 |
| 确认取走 | 核对箱体及握手条件 | PLC 有效状态与实际箱体一致 |
| 运至等待位 | 执行运输，报告约定到位状态 | 原运输完成，PLC 正确接收握手 |
| 等待设备就绪 | 条件不满足就明确等待 | 有效的设备就绪/允许信号 |
| 进入并倒料 | 按双方责任执行动作，等待完成 | 车端/PLC 各自提供对应动作的证据 |
| 返回放空箱 | 运输、放箱，核对工位反馈 | 放箱动作及约定箱体状态成立 |
| 收尾 | 复位约定输出、记录结果、按已验证条件释放资源 | 握手达到约定最终态，无遗留任务/占用 |

交付：真实任务日志、PLC 读写时序、车端编号对应、现场操作说明。

出口：呼叫、取满箱、倒料、返空箱、收尾可连续完成约定轮次，所有输出的最终状态正确。轮次在联调前共同确定并记录，不用模拟次数代替。

需重点复核：现有九步模拟报告说明第 9 步在输出复位成功后结束，不等待下一轮 PLC 读回。现场必须明确“写成功”是否足以结束握手，还是要读回/PLC 应答/状态机确认；多位写入、PLC 扫描顺序和中途断连均要覆盖。不能仅凭 HSL 调用成功就推导设备完成了业务动作。

### P5：异常恢复先于多车放量

基础防重复和资源保留从 P3 起就要存在；本阶段集中验证异常，不是正常流程跑完后才补异常设计。

| 场景 | 需要验证的行为 |
|---|---|
| 车端收到命令但后台丢失应答 | 保留原编号、核对原任务；不能因超时直接生成新命令 |
| PLC 断连或数据过期 | 停止依赖该条件推进，不把旧真值当当前许可 |
| 设备故障/长时间未就绪 | 明确等待或故障，保留关联任务和必要资源 |
| 导航失败、取消延迟、历史缺失 | 不误判完成；未知结果不自动解锁或重发 |
| 后台重启、客户端关闭/重开 | 恢复原任务关联；没有证据时不自动恢复危险步骤 |
| 人工移车/取放箱、地图或参数变化 | 原执行依据失效时阻止盲目继续，展示具体处置项 |
| PLC 写入中途断连 | 核对可能部分写入的状态，按握手约定恢复，不能直接清空全部输出 |

交付：异常用例记录、恢复操作步骤、问题闭环清单。

出口：原任务、命令、PLC 状态、载荷和资源能关联核对；操作员清楚何时可恢复、取消或关闭，后台执行必要检查。

### P6：两车起步，验证最少必要交通资源

前置：P4、P5 通过；两车地图、尺寸/载荷、停靠位置和资源边界核定。

工作：

1. 从一个共享通道或倒料区域开始，配置明确容量及等待位置，验证同时呼叫、不同优先级和排队。
2. 验证同向追车、相向进入、不同路线交叠；按实际存在的场景选择用例。不能只给路段编号加锁而忽略几何相交。
3. 验证等待车辆不会占住前车退出所需区域，进入前具备可用等待/退出空间。
4. 采用当前已有、可以证明有效的保守占用及释放方式；可能降低吞吐，应测量影响，避免一次申请造成循环等待。
5. 任务完成、租约超时、连接断开或画面位置越界，单独都不能作为所有资源释放依据。释放必须对应已核定的车辆及载荷退出条件。
6. 缺真实进度来源、车体包络和定位误差证据时，不启用逐段自动释放。资料齐全后再独立验证和优化。

交付：资源地图、冲突用例、排队及释放记录、吞吐测量。

出口：不会向两车同时授予互斥区域；异常车资源不会误释放；正常车能完成任务，不产生无法解释的长期等待。首期不承诺厂家 Core 等级的全局多机器人规划能力。

### P7：有限范围试运行和交付

工作：先少量工位/车辆，再按实测结果扩展；检查长时间运行、数据库和日志增长、备份恢复、权限、服务启动和操作员使用。

交付：部署配置清单、版本及哈希、恢复/备份说明、现场验收记录和剩余问题表。区分阻断交付的问题与已确认可后续处理的问题。

出口：按双方约定的业务规模、持续时间和异常用例验收。以现场记录判断，不以测试断言总数或截图数量判断完成度。

## 8. 下一轮具体顺序

1. 形成一辆车、一个取料工位、一个倒料设备的接口表，核定现场是否总控 PLC 统一汇总。
2. 核实试点点表中推导地址和实际动作，建立九步责任与完成证据表。
3. 取得本车地图和只读返回，完成导入、绑定及两侧数据核对。
4. 根据真实差异修复现有实现，运行单车导航/动作，再运行完整任务。
5. 集中验证断连、取消、重启和握手复位，再扩大到两车冲突。

每批开发记录“解决的现场问题、改动、证据、未验证项、下一阶段出口”，避免只报新增功能和测试数量。

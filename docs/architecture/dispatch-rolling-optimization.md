# 滚动全局派车与影子比对

适用主工程：`AgvDispatch.sln`；协议仍为快捷 AGV / Robokit TCP。本文对应 2026-11-03 的实现，不增加旧项目功能或变更车端协议。

## 六层实际执行链

| 层 | 实际模块 | 输入与输出及职责边界 |
| --- | --- | --- |
| 1. PLC 呼叫队列 | `TaskCreationCoordinator`、`DispatchTaskRepository`、`DispatchQueueWindowService` | 先持久化呼叫及九个原步骤，按活动工位和请求编号去重；PLC 应答失败沿用原任务重试。窗口读取原优先级、原呼叫时间及未派发任务，固定已执行/持有路权的任务与车辆。 |
| 2. 候选筛选 | `DispatchCandidateFilter` | 健康、定位、电量、车辆池/指定车辆、换单责任、区域、路线筛选及成本估算；输出候选图与等待建议，不能授予或释放路权、登记或发送命令。车辆能力仍以当前明确配置的车辆池约束为准。 |
| 3. 滚动全局匹配 | `DispatchAssignmentOptimizer` | 纯计算最小费用最大流，返回推荐和理由；不访问 PLC、不申请路权、不修改任务。 |
| 4. 交通路权 | `DispatchTrafficReservationService`、`TrafficResourceManager` | 接受规划建议，持久化资源申请、校验容量与公平顺序，整条路径取得后才交给下一层。完成任务清理在此层显式执行；不可用资源查询本身只读。正常交接释放与异常保留仍由原生命周期管理。 |
| 5. 安全复核 | `DispatchPreSendSafetyService` | 传统派车、全局派车、后续运输段在命令登记前，以及 Outbox 领取前，复用同一复核服务；检查地图、原任务/步骤/车辆、实时健康及位置、实际路权和当前阶段真实 PLC 条件。28 阶段复用持久化绑定/原阶段许可；旧契约读取真实点表缓存的值、质量及采样时间，不添加虚构许可位。 |
| 6. 执行与恢复 | `AgvCommandOutboxRepository`、`AgvCommandOutboxDispatcher`、`PersistentHandshakeExecutor`、`ExecutionRecoveryWorker` | 原子登记命令与车辆责任，领取成功的调用才可发送；任务、步骤及厂家幂等编号跨重启保留。发送后以原身份核对回执和反馈，执行交接、恢复或等待人工复核；不重建原任务、不抢占已派车辆。 |

编排器只负责按层协调和失败后重算。匹配推荐 → 取得路权 → 安全复核 → 原子命令登记 → 发送前再次复核 → 原命令发送/恢复，是实际调用链。后续倒料和返程运输同样经过第 4、5、6 层。

### 车端障碍自动恢复与六层的关系

障碍来源是车端 `Blocked=true` 或非致命 `52200`，后台不能仅凭速度为零推断障碍。`ObstacleRecoveryCoordinator` 是设备观测后的恢复协调器，不替代六层：

1. 原业务任务、步骤、载荷和PLC责任保持不变，不重新建单。
2. 连续受阻达到10秒后，先核验原车端任务终态、连续停稳、当前可信位置、原任务目的站、运行地图方向、道路封锁、不可用交通资源和车辆包络；原任务未释放时只保留候选，不发送第二条导航。
3. 候选仍由第4层申请整条路径路权，并由第5层复核地图、车辆停稳、定位、PLC/28阶段证据和原任务身份。
4. 第6层只允许一条替代发送意图。原3066任务链未全部终态时绝不发送第二条；取消请求必须等待全链终态。
5. 替代3066发送后绑定回原业务任务和原步骤，继续接受到点、动作、PLC和路权交接核验。发送结果未知时只查询新编号，禁止重发。
6. 30秒预警、60秒报警、120秒建议封锁实际受阻方向及必要上游汇入。无安全替代路线时推荐安全点并冻结原任务；不会自动释放载荷、PLC责任或路权。

原 Outbox 的发送路线快照保持不可变。自动改道不会改写历史快照，而是把原命令标为已取消，并为同一业务步骤新增一条带新3066根编号、新路线快照和新路权依据的受控替代命令；原业务任务和步骤编号不变。取消、替代发送和任务重绑定全部在同一个地图执行控制租约内，避免正式编排器把预期取消中间态并发写成另一条故障。

这些规则保持“队列 → 候选 → 匹配 → 路权 → 安全 → 执行”的实际责任边界。障碍恢复不是第七层，也不能绕过其中任何一层。

Web 页面按六层显示最近一次真实观察、数量、原因、时间以及任务受阻层。未启用、尚未观察、已过期或被阻止均单独显示；某层“就绪”只表示该次检查结果，不授予后续车辆或 PLC 动作权限。即使业务派车关闭，队列与待发送命令数量仍从原数据库只读查询。

独立的“六层调度监控”页 `/#/dispatch-pipeline` 可按层查看实际开关、输入输出、逐项条件和任务/车辆/资源/命令记录，并冻结某次观察或选择本页最近观察；滚动派车页保留推荐及策略配置。数据来源、样本数量、时间与历史边界见 [六层监控说明](dispatch-pipeline-monitor-20261103.md)。

已发生物理发送尝试的原命令，恢复时不能要求车辆仍在原起点或本轮 PLC 许可尚未消耗：先保持原步骤编号、原责任、地图与路权，由 Robokit 查询原编号核对是否接受；未取得明确证据不能改成新任务自动重发。无发送尝试的新命令仍必须满足完整实时复核。

## 使用入口与模式

日常入口继续为 `http://127.0.0.1:5199/`，导航中选择“滚动派车优化”，完整页面地址为 `http://127.0.0.1:5199/#/dispatch-optimization`。页面显示等待任务、窗口数量、车辆候选、估算成本、全局推荐、传统算法选择、实际命令登记及未派发原因。

| 模式 | 行为 |
| --- | --- |
| `Shadow`，默认 | 滚动计算推荐并与相同候选图上的传统贪心比较；实际派车继续现有编排流程。 |
| `Global` | 后续等待任务使用全局推荐，逐项申请路权、重新核验并登记持久化命令。 |
| `Disabled` | 关闭优化计算，使用传统派车。车辆健康、执行门禁及已有路权仍须满足。 |

“全局推荐”和“实际登记”分开显示：推荐尚未取得路权时，实际登记为空是有效结果。候选详情包含排除原因及行驶、交通、返程、低电量、跨区、待机加分。页面只保留当前浏览过程中读取到的最近 20 轮观察，刷新页面后重新累计；它不是持久化审计日志。

建议先保持影子比对，核对仅某台车能执行的工位、多车共享公共资源、离线或低电量、长时间等待等场景，再在策略中选择全局匹配并保存。保存需要现有管理员权限；界面演示或工程模拟上下文不能保存现场策略。策略保存不打开任务执行、PLC 写入或单次导航许可。

| 参数 | 默认值 | 作用 |
| --- | --- | --- |
| 滚动周期 | 3000ms | 允许 2000～5000ms；后台原有执行状态同步继续独立进行。 |
| 任务窗口 | 80 | 建议 50～100；窗口外任务仍在原持久化队列。 |
| 每车保留候选 | 15 | 建议 10～20，缩小匹配图。 |
| 每任务保留车辆 | 2 | 唯一可执行车辆保留；额外可行性修复防止候选裁剪破坏最大匹配。 |
| 等待补偿 | 每分钟 1 分，上限 30 分 | 从原始呼叫时间计算，只加一次。 |
| 截止紧迫窗口 | 15 分钟，最多加 30 分 | 仅设置了工位呼叫时限时生效。 |
| 业务最低电量 | 20% | 与原有充电责任门禁同时生效。 |
| 待机加分 | 1 秒 | 最多抵扣 1 秒，不能覆盖明显更长的空驶。 |
| 低电量成本 | 10 秒 | 按剩余电量计算软成本，不代替业务最低电量。 |
| 跨区成本 | 10 秒 | 起点与取货点都明确配置业务区域且区域不同时生效。 |
| 返程权重 | 0.2 | 使用配置待机点的可达返程估算；设为 0 关闭此成本。 |

区域配置使用真实 AGV 站点编号；工位时限配置使用任务工位编号，从原始呼叫时间起算。系统不根据地图坐标猜测业务分区，也不为未配置时限的工位补造截止时间。

策略默认值可由 `DispatchOptimization` 配置节提供。通过界面保存的修订保存在后台数据库同目录的 `dispatch-optimization.json`，日常数据目录仍是 `发布包/运行数据/后台5199`。保存校验参数和预期修订，使用临时文件原子替换；旧页面不能覆盖别人刚保存的修订。配置文件损坏时关闭优化并保留传统派车，后台记录读取错误。

## 优化顺序与固定责任

纯计算模块 `DispatchAssignmentOptimizer` 不访问数据库、不申请路权、不发送车辆命令。采用逐次最短增广路的最小费用最大流；成本采用分层比较，避免把“优先级分数”和“秒数”直接相加后被较长路线反向覆盖。

优化顺序为：最大可执行匹配数，在该数量下最大化有效优先级总和；再按呼叫先后、预计到达成本、返程及其他软成本选择，最后按稳定编号处理等价解。有效优先级为基础优先级、等待补偿、已配置的截止时间紧迫度之和；跨区作为候选软成本，不能扩大车辆池或绕过路线限制。

候选来自当前真实等待任务与可用车辆。离线、定位异常或过期、急停、阻挡、阻塞报警、未知健康状态、低电量、工位车辆池限制、指定车辆限制、受控换单、充电责任以及不可达路线均先排除。

正在执行、已登记命令、已有车辆责任或持有任何实际交通租约的任务保持原责任。持有租约的车辆同样排除，即使其任务未记录车辆、已故障或心跳过期。优化器不抢占这些车辆。临近完成任务的车辆在实际完成、原责任及路权交接结束后进入后续周期；当前实现没有以预测完成时间提前派第二单。

## 路权、公平性与发送复核

1. 按有效优先级、呼叫先后逐项申请匹配后的路径资源。
2. 容量不足时保持原任务等待，失败候选从本轮剩余图移除，再匹配其他候选。
3. 公共资源释放后，先核对仍有效等待请求的优先级与呼叫时间，后来的同优先级请求不能凭重试顺序插队；容量大于 1 时按剩余容量判断。
4. 前序请求被其他已满资源阻挡、不能一次取得整条路径时，不替它空占当前可用容量。
5. 已取得的有效路权不因新优先级、超时或优化重算而撤销。心跳过期仍是实际占用；正常交接、完成或现有人工处置流程负责释放。
6. 命令登记前重新检查地图、车辆、责任、路径及路权；outbox 真正认领发送前，再核对持久化申请的原步骤、任务、车辆、地图版本和起终点，以及全部资源的实际租约。缺失、等待中、已释放、归属不一致或资源记录损坏时不认领、不增加发送尝试；明确无需资源的路径须有 `NotRequired` 及空资源清单。后续发送继续经过地图/封路执行门禁。

队列优先级是滚动计算的推荐元数据，需在最近 10 秒内被重新观察才参与插队校验，同时必须属于同一地图、有效业务任务及待执行步骤。失效的推荐不会永久挡住其他可执行任务。此有效期只作用于**尚未授予的排队推荐**，绝不使物理路权租约过期或释放。排序使用原任务呼叫时间，候选车辆变化不会重建呼叫时间。

## 路线缓存与规模

`DispatchRouteCache` 为最多 2048 项的 LRU，缓存可达和不可达结果。键包括运行地图身份/版本、起终点、道路封锁就绪状态及修订、不可用资源集合、动态交通惩罚、占用站点、受保护待机点与路由配置。条件不变时跨周期复用；计算或读取时条件变化则丢弃结果。最终准备命令前重新调用实际路线规划器，缓存结果本身不授予发送许可。

默认先取 80 个等待任务，再按车辆池和健康等条件计算候选；匹配阶段保留每车最佳 15 条及每任务最佳 2 条，并保护稀缺车辆的可行匹配。并非每轮重算全部历史任务或 300 个未呼叫工位。页面的缓存命中/未命中与耗时用于观察本场地图的真实开销；不把其他电脑上的“毫秒级”作为现场性能验收值。

## 当前边界与验收

- 成本是地图与配置推导的估算，不是车端承诺的到达时间。资源容量已满时保持等待；缺少释放时间依据时不编造剩余等待秒数。返程为待机点路线代理成本，不是整个取箱、倒料、空箱返还工艺的精确完工时间。
- 车辆能力按已配置工位车辆池和任务指定车辆执行。当前车辆数据模型未提供独立的车型能力矩阵，不能声称已自动识别所有车型与工位兼容性。
- 等待补偿有上限，在持续超负荷、始终有更高基础优先级任务到达时，不保证严格无饥饿；应结合等待页面监测、工位时限与现场容量调整。
- 运行中已有任务、资源交接、持久化命令与异常恢复仍使用主工程既有机制；优化不重新生成历史任务，不清空队列，也不自动解除故障任务占用。

# 已接单车辆的滚动续行

运满箱和返空箱在原任务下比较全程可通的路线与可先到达合格停靠点的路线。后者将后段占用计入预计成本，首段和独立候车位仍按原队列原子申请。倒料区驶出保留出口保护。

正在执行的滚动窗口可按路权变化预算剩余路线。缓存的预算只供比较，车到窗口终点并确认停稳后重新读取路权与路线，才可申请下一段。续行保留已完成窗口、原步骤起终点、候车位绑定和末段动作，替换尚未执行的窗口。没有可用替代路线时保留原申请，继续等路权。

同一运输步骤的自动改线须向尚未完成的窗口推进。排除重过已完成窗口停靠点的替代路线。按路长和限速比较剩余路线，绕行耗时超过原路线 1.5 倍且多 30 秒以上时，保留原申请并继续复核，最多优先等 120 秒。临时占用解除即可沿原路线续行，持续占用后再重新比较可用旁路；恢复流程可独立处理确需回退的故障。

隔离验收沿用 B07 五车十单的地图、呼叫和模型速度，记录第二次 CNC-111 运满箱发车、CNC-177 窗口资源数量、车尾确认至释放、总完赛及安全闭环。

动态续行会合法改变同一业务步骤的后续窗口数量，验收器不能把“计划改为更多或更少的安全段”本身判为重复或遗漏。每个业务步骤仍须满足以下条件。已发窗口的 `windowIndex` 从 0 连续递增。每个 `windows` 快照的索引连续，且只有末段为 `final=true`。每段起点承接上一段终点。厂家任务编号按发出顺序构成 `previousVendorTaskId` 链。最后一段回到原业务步骤终点。已经实际发出的窗口作为历史前缀保留，改线只替换尚未发出的后续窗口。

### 路权申请的数据库开销

每次申请在同一事务中读取活跃租约，按资源归集占用任务，并读取有交集的有效排队信息。计算前序时仍核对其完整申请是否可获得，已有租约可继续续期。全部资源通过后统一续期和新增租约；任何一项被前序申请或现有占用挡住时，记录首个阻塞并保持原有租约。事务中的信息仅用于本次申请。

`dotnet run --project tools/DispatchTrafficFairnessSmokeTest` 同时验证容量、前序、公平性和路权归属。126 项资源的申请只读取一轮租约和公平队列，随后批量写入。另一个请求占住其中任一项时，不得给本次失败申请新增任何一项租约。

### 运行地图复用

运行地图激活时确定地图摘要与自动通道拓扑。派车、候车和续行按当前地图快照复用摘要与路段索引，换图后使用新快照。路线切窗只读取路径覆盖的节点和路段，自动通道资源与路由图使用同一份拓扑。路权和封路复核仍读取当前状态。

### 车辆占道定位计算

活跃地图复用有效道路的几何索引和保守外包范围。每次候选规划仍检查最新的车位、反馈时间和置信度。定位在图上查找最近路段时，只跳过已证明比当前最近路段更远的几何，等距时沿用地图顺序。激活新地图后使用新索引。发送前的路权和封路复核继续独立执行。

`dotnet run --project tools/MapTrafficSmokeTest` 核对直线、曲线、等距、旧反馈和换图。B07 基准比较相同位置样本得出的路段与距离，并记录定位计算耗时。

### 已通过资源的租约提交

SQLite 可能以带末尾零的文本保存获取时间。到站或行驶中释放时，先在同一事务中将租约读成类型化记录，核对原租约编号、任务、步骤、车辆、地图与资源归属，再按这些身份字段删除。到站释放还核对精确获取时间。读取和删除一起提交，删除数量与已核对的数量一致才记录事件并唤醒调度。

`CompletedRouteReleaseSmokeTest` 和 `SegmentTrafficHandoffSmokeTest` 覆盖旧库时间格式、同批原子释放、边界保留、反复消费和他车重获资源。

### 车端地图核验与派车登记

Global 按同一批候车点核验车端地图身份以及四段运输的相邻有向边。同一次核验只查询一次初始地图状态，已验证过的有向边复用结果，结束时再次确认车端地图身份和载入状态。隔离仿真核验同源地图的有向边，现场继续使用 Robokit 路径查询。

等车端只读核验期间，释放地图执行门禁和充电业务锁，已有命令可以发送，车尾确认通过的租约可以提交释放。核验完成后重新取得门禁，核对地图与策略、倒料配置、任务阶段、并发剩余量、车辆责任和即时路线，再申请首窗口和登记命令。车端核验的结果不能单独授予路权或发送许可。周期日志记录候选构建、车端核验和锁内登记耗时。

`DispatchOptimizationIntegrationSmokeTest` 使用可暂停的车端核验，核对核验期间旧命令仍能发送，以及关门、换图或任务变化后旧核验结果不能登记。

### 隔离验收采样

一次验收采样按资源编号归集已经存在的租约。容量和等待环检查通过同一个索引读取资源持有任务，空闲资源无需重复扫描租约。重复租约仍按不同任务数核算容量。采样频率、车体包络检查和报告结构沿用当前规则，便于与旧报告对照。采样开销单独计时，车辆物理速度和回放倍率各自配置。

全链路运行倍率的验收需要在隔离实例内区分仿真时间与真实耗时。虚拟车的速度、加速度和耗电按仿真秒积分，呼叫、PLC 等待、反馈时效、释放确认和超时判定使用同一时间基准，网络与进程看门狗使用真实时间。先以一单对照 1× 与 2× 的事件顺序、物理速度和报告时间，再用 B07 五车十单复核安全、收尾与有效倍率。


### 隔离运行倍率

运行倍率属于当次隔离实例，支持 1×、2×、4× 和 8×，在启动前选择。1× 用于和现场实时链路复核，2× 用于正式验收对照，4× 用于缩短演示等待，8× 仅用于负载与安全边界压测。以实例共同起始时刻和各进程的单调计时推导仿真日期及经过时间。虚拟车模型里的米每秒、运动积分步长及电耗配置分别记录。正式后台只有在隔离进程和设备全为回环且使用独立库的条件下启用这个时钟。默认和现场继续使用系统时间。

业务呼叫、PLC 到位反馈与延时、导航反馈、任务和租约的持久化时间、路权老化及业务超时采用仿真时间。调度和采集的周期按倍率缩短，传输超时、进程就绪检查、验收采样预算继续按实时时间处理。报告同时记录设定倍率、实际墙钟耗时和模拟耗时。倍率在启动前确定。先核对普通九步业务，故障场景沿用 1× 的验收设置。

## 关键实现

- `DispatchTaskOrchestrator` 和兼容派车路径均改为“先申请当前安全窗口，车辆到达后再滚动申请下一窗口”。
- 全局匹配在执行前再次核对任务、车辆实时位置、地图版本、PLC 许可和实际路权。
- 返程恢复可以识别“当前窗口已完成且车辆在窗口终点停稳”，不会把中间窗口误记为整个业务步骤完成。
- 地图节点比较统一支持 `BUS-*`、厂家 `LM*` 和唯一别名，避免相同节点因命名方式不同而失配。
- 障碍恢复使用任务步骤作为持久生命周期身份，同一步骤再次受阻只更新原记录。
- 完成路线释放不再要求所有资源都有几何多边形，但仍要求车辆到达明确终点、无活动车端任务、安全状态正常，并保留终点资源。

## 调度算法变化与新旧对比

今天调度算法的核心变化，是由“首段命令一次占用整条路线”改为“按安全点拆分、滚动申请和释放路权窗口”。

| 对比项 | 旧算法：整路线预占 | 新算法：安全窗口滚动路权 |
| --- | --- | --- |
| 首段申请范围 | 从车辆当前位置到最终目的地的全部道路和资源 | 只申请最近的第一个安全窗口 |
| 后续路段 | 一次性锁定到原任务结束 | 车辆到达窗口终点后，再申请下一窗口 |
| 已走过路段 | 通常等整条任务结束才统一释放 | 下一窗口取得后，立即释放不再复用的前序路段 |
| 上游车辆影响 | 可能提前占用下游汇合区和倒料入口 | 未到达前不能提前占用下游共享资源 |
| 多车并发能力 | 容易变成串行，局部等待会放大为整组等待 | 各车可在自己的安全窗口内并行推进 |
| 路权冲突处理 | 往往整条路线互相阻塞 | 只在当前窗口冲突处等待，通过后继续前进 |
| 恢复难度 | 状态简单，但容易长期死锁 | 状态更细，需要严格记录窗口索引、原命令和地图身份 |
| 安全性 | 保守，但过度占用会产生新的阻塞 | 仍保持发车前、到窗口终点和多车安全复核，异常时 fail-closed |
| 吞吐量 | 低，尤其不适合多车共用主通道 | 较高，适合多车、多工位和共享汇合区 |

新算法没有取消安全保守性。车辆到达窗口终点后，必须同时满足以下条件才会续接：车辆 Online/Good、位置新鲜、停在确定安全点、零速、无急停、无阻塞报警、原车端任务已完成、地图版本未变化、下一窗口路权申请成功。任一条件不满足时，车辆保持在安全点，原任务和责任不丢失。

新算法改变了“先占整条路”的做法，但没有允许后车在运行中抢占前车。已经进入单车道窗口的车辆继续完成该窗口；其他车辆按有效任务优先级和资源排队顺序申请下一窗口。这样既避免中途抢占造成碰撞风险，也让等待发生在明确安全点。

### 哪种方案更适合当前真实项目

当前项目存在三车、七工位、共享汇合点、两个等待位和一个容量为 1 的倒料区，正常运行应使用新的“安全窗口滚动路权”算法。今天现场出现的 LM40 互锁、前车未到下游却提前占用道路、车辆通过后资源迟迟不释放，都属于旧整路线预占方式在真实多车场景中的直接副作用。

短距离单车道、窄通道或必须完整容纳整车的独占区可以使用“整个小资源区临时独占”作为新算法的窗口策略。也就是说，整段独占只应作为某个必要的不可拆分安全窗口，而不能再把整张任务路线都当成一个窗口。

因此当前项目的推荐规则是：

1. 普通道路、双向道路和长通道使用滚动窗口。
2. LM39 倒料区、唯一倒料入口等容量为 1 的资源使用完整资源独占。
3. 车辆只能在可停车安全点等待下一窗口。
4. 任务优先级用于给等待队列排序，不抢占已进入危险窗口的车辆。
5. 车辆离线、定位过期、急停、持续阻挡或窗口地图不一致时冻结续接，不自动猜测和重发。

## 今天测试覆盖的典型场景

- 多工位同时呼叫时，系统按车辆健康、地图可达、路线成本、有效优先级和当前路权筛选车辆，不固定绑定“某车只能做某工位”。
- 两车接近 LM40、LM33、LM39 等共享区时，只允许当前窗口持有者进入；另一车在安全点等待，前车通过后释放前序资源。
- 正常交通避让和短暂 Blocked 不再被直接判成全组故障；只有持续无法恢复、急停或非正常报警才进入异常恢复流程。
- 同工位重复呼叫复用原任务，不重复创建任务、步骤、PLC 握手或车端命令。
- 多窗口返程按窗口续接，原业务步骤保持 Executing，直到最终返箱和出区交接闭合。
- 完成运输到站后释放已走过路段，保留终点、仍在车体覆盖范围内的资源以及该任务仍需负责的设备资源。
- 离线车辆在候选阶段被排除；原命令不会由其他车辆冒领，也不会因恢复轮询重复发送。

## ImageSharp 安全升级结论

- 漏洞来源是直接依赖 `ACadSharp.Image 0.1.6` 带入的间接依赖 `SixLabors.ImageSharp 3.1.12`。
- 6 个公告的修复边界都是 ImageSharp `3.2.0`：4 个 High、2 个 Moderate。
- 已尝试锁定 `SixLabors.ImageSharp 3.2.0` 和配套的 `SixLabors.ImageSharp.Drawing 2.2.0`。
- 两个安全版本均启用了 Six Labors 商业许可证构建检查；当前工程、用户目录和环境变量中都没有 `sixlabors.lic`、`SixLaborsLicenseKey` 或 `SixLaborsLicenseFile`。
- 实际构建被以下条件阻止：`No Six Labors license found`，解决方案无法完成升级。
- 未通过跳过 build target、屏蔽 NuGet 审计、改写包元数据或其他方式绕过许可证，也没有用 `NoWarn` 隐藏漏洞。
- 已恢复没有直接锁定 `ImageSharp` 的可编译基线，当前仍解析为 `3.1.12`；完整解决方案验证为 0 编译错误。
- 当前实际使用范围只包括可信 Smap 的像素缓冲 PNG 输出和本地 DWG/DXF CAD 底图渲染，没有开放 TIFF、BigTIFF、传真编码、ICC CLUT 或直方图均衡输入。这能缩小攻击面，但不等于修复漏洞。

要完成正式升级，需要项目取得有效的 Six Labors 商业许可证并放置许可证文件/配置构建密钥；随后恢复安全版本依赖，重新构建完整解决方案，并重跑 MapTraffic、MapEditor、CadDetailPipe、NativeSmap 和 PointCloud3D 回归。若不能取得许可证，下一替代方案是移除 `ACadSharp.Image` 与 `ImageSharp` 依赖并替换 CAD 栅格渲染实现，工作量明显大于补丁升级。
